## Project Overview

**Cave — Inventaire** is a single-page wine cellar management PWA for a private Bordeaux-focused collection. It is entirely self-contained in one file: `index.html`. There is no build system, no npm, no bundler — just open the file in a browser or serve it statically.

## Second App: Cave — YD (mobile)

There is a **second, separate app** deployed at `wine-app-yd.netlify.app` (Netlify site id `bdc28751-6d21-4eda-9493-d61fb9fba445`), preferred by the user on phone for its readability. It has no relation to `index.html` architecturally, but now shares the same Supabase project/schema.

- Source lives at `App/Cave-YD-mobile.html` — a plain single-file React app loaded via in-browser Babel (`<script type="text/babel">`, CDN React/ReactDOM/Babel-standalone from cdnjs), no build step.
- **September 2026 rebuild**: the original file was a Claude-Design "bundler" export (all assets base64-inlined in a `__bundler/manifest` block, unpacked to `blob:` URLs at runtime, plus an `IOSDevice` bezel component for the design-tool preview vs. a `CAVE_PRODUCTION`-gated real-viewport path). That whole scaffold was dropped in favor of a plain file — it was the root cause of the tab bar's hardcoded `paddingBottom:26` (not derived from `env(safe-area-inset-bottom)`, which is now used via `max(env(safe-area-inset-bottom,0px), 8px)`). Fonts load via a normal Google Fonts `<link>` instead of embedded woff2 base64. If you need to reconstruct historical context from the old bundler export, its manifest entries can be gunzip-decompressed from base64 — see git history before commit `f55fbef`.
- **Design system**: same warm-cream Bordeaux palette as `index.html` (`--paper:#F6F2EB`, `--wine:#6E1F2B`, `--brass:#A9833F`, etc., defined as CSS custom properties) but Cormorant Garamond serif is used more heavily (list rows, big editorial page titles like "La *Cave*") and pairs with system-ui sans rather than Inter. The app deliberately has **one fixed theme** — it does not follow `prefers-color-scheme`; do not add a dark-mode block (WebKit doesn't reliably resolve `var()` inside raw SVG presentation attributes on older versions either — pass hex literals via the `C` JS object to `Icon`/SVG `color`/`fill`/`stroke` props, not `var(--x)` strings, to avoid icons silently losing their color).
- **`<meta name="format-detection" content="telephone=no, date=no, address=no, email=no">`** is required in the real head — without it iOS Safari auto-linkifies numbers that look like dates/phone numbers (e.g. vintages, prices) and renders them blue/underlined.
- **Data layer**: `App/Cave-YD-mobile.html` has its own inline plain-JS Supabase adapter (`window.CAVE_LIVE`, same `SUPA_URL`/anon key as `index.html`) — not `sbFetch`. It maps the live `wines`/`tastings` schema (see `index.html`'s "Data Layer" section for column names) to the mobile UI's model via `mapWine`/`mapTasting`, deriving `region`/`color` from the free-form `vin` (appellation) column through a regex table (`APPELLATION_RULES`) since the mobile app's card/map UI wants a region+color the DB schema doesn't store directly. `WINES`/`TASTINGS`/`PRIMEURS` are mutable `let` arrays mutated in place by `loadLiveCellar()` (`.length=0` + `push`), matching the `index.html` pattern of one shared array all screens read — after any write, call `reload()` (in `App`) rather than only closing the modal, or screens will show stale data. Login is required before any screen renders (`Login` component, `CAVE_LIVE.signIn`); writes need auth per the `wines`/`tastings` RLS policies documented under "RLS policies" below — anon writes correctly 401/403 with a row-level-security error, which the UI surfaces as "Connexion requise".
- **Editing an existing wine** (added September 2026): `AddWine` (`App/Cave-YD-mobile.html`) now doubles as the edit form when rendered with a `wine` prop — `App`'s `modal` state grew an `{ edit: wine }` case alongside `'add'`/`{ log: wine }`, reached via a new pencil `edit` button in `WineSheet`'s action row (previously a dead, unwired button there — it had no `onClick` at all). On mount in edit mode, `AddWine` does **not** prefill the form from the `wine` object passed in — `WINES`/`w.btl`/`w.mag` are the *remaining* stock (already reduced by logged tastings, via `loadCellar()`'s drunk-count subtraction), not the raw `bouteilles`/`magnums` DB total, so prefilling from them and PATCHing back would silently shrink the total by however many bottles had already been logged as drunk. Instead it calls the new `CAVE_LIVE.getWineRaw(id)` (a plain `supaSelect` on `wines?id=eq.<id>`) and populates the form from that raw row. Saving calls the new `CAVE_LIVE.updateWineLive(id, f)` (a `supaUpdate`/PATCH) instead of `addWineLive`'s insert. `updateWineLive`'s PATCH body deliberately includes only the fields the form actually has controls for (`domaine`, `vin`, `millesime`, `bouteilles`, `magnums`, `prix_bouteille`, `livraison`, `livre`, `drink_from`, `drink_to`, `type`, `date`) — it leaves out `prix_magnum`, `note`, `critic_*`, and `shelf`/`slot_col`/`slot_row`, none of which this form exposes, so editing a wine from the phone can't silently wipe a value that was only ever set from `index.html` or the critic research pass (same reasoning as `wineToRow()` excluding critic fields on the laptop app). The "Scanner une étiquette" card is hidden in edit mode (it's for prefilling a new entry from a photo, not for editing one that already exists) and the sheet shows a loading spinner while the raw row fetch is in flight.
- **Label scanning** (added September 2026): `AddWine`'s sheet (`App/Cave-YD-mobile.html`) has a "Scanner une étiquette" card above the form fields — a hidden `<input type="file" accept="image/*">` (no `capture` attribute, so iOS/Android offer both "Take Photo" and "Choose from Library") triggered by a visible button. `fileToResizedJpegBase64()` reads the picked file, downscales it on a `<canvas>` (max 1100px on the long edge, JPEG q=0.82 — keeps the upload small/fast since phone camera photos can be several MB) and returns base64. `handleScan()` POSTs `{image, mediaType:'image/jpeg'}` to the **`scan-label` Supabase Edge Function** (`${SUPA_URL}/functions/v1/scan-label`, called with a plain `fetch` + `apikey` header like `drinking-window` — not `CAVE_LIVE`'s Supabase adapter, edge functions aren't REST-table calls) which proxies to `claude-haiku-4-5-20251001` with a vision content block and returns `{domaine, vin, millesime}` (nulls for anything unreadable); the response prefills those three `AddWine` form fields (`domaine`, `appellation`, `mill`) but never touches bottle count/price/drinking-window/etc. — the user still reviews and completes the rest before saving. Deliberately mobile-only — `index.html` (desktop/laptop) keeps its "Coller depuis Claude" paste-JSON flow instead; camera label scanning isn't wanted there, per the user.
- **Redeploying**: Netlify's site-level MCP `deploy-site` tool takes no directory/path argument and isn't reliable for this single-file, non-git-linked site (it timed out / 502'd when tried). The verified working method is the raw Netlify API digest-deploy flow, run manually via `curl` with a user-supplied personal access token (`app.netlify.com/user/applications`):
  1. Check the currently *published* deploy's file list first (`GET /api/v1/deploys/{deploy_id}/files`) — the site serves more than just `index.html` (currently also `/apple-touch-icon.png`, `/favicon-32.png`, `/manifest.json`); a deploy that omits a currently-live file removes it, so always include all of them (unchanged files just need their known sha1, no re-upload).
  2. `POST /api/v1/sites/{site_id}/deploys` with `{"files": {"/index.html": "<sha1>", "/apple-touch-icon.png": "<sha1>", "/favicon-32.png": "<sha1>", "/manifest.json": "<sha1>"}}` — the response's `required` array lists which ones actually need uploading (content-addressed; unchanged files are skipped).
  3. `PUT /api/v1/deploys/{deploy_id}/files/<path-without-leading-slash>` with the raw file bytes, for each file in `required`.
  4. `POST /api/v1/sites/{site_id}/deploys/{deploy_id}/restore` to publish it live.
  The token is only needed for the duration of the deploy; the user can revoke it after.
- The Netlify project `my-cellar-yd` (site id `af0c6c49-008c-4578-a41e-c135b25a7c5b`) is the deployed copy of this repo's `index.html` — the laptop-preferred, more detailed app.

## Architecture

Everything lives in `index.html`, structured as three logical sections:

1. **CSS** (lines ~13–1930): All styles, including CSS custom properties (`--ivory`, `--oxblood`, `--gold`, etc.) that define the Bordeaux label aesthetic. The design language is Cormorant Garamond (serif headings) + Inter (sans-serif data). Never introduce Bootstrap or Tailwind — the design system is bespoke.

2. **HTML** (lines ~1930–2660): The app shell with a sidebar nav (240px fixed) and main content area. Pages are toggled via CSS classes (`active`), not routing. The seven pages are: `cave` (inventory), `queboire` (what to drink wizard), `historique` (tasting log), `cellier3d` (3D fridge visualization), `valeur` (portfolio value), `analyses` (charts), `primeurs` (current-year primeur campaign tracker). After the app shell closing tag, two mobile-only elements are rendered: `<header class="mobile-header">` and `<nav class="mobile-bottom-nav">` — hidden by default, activated via `@media (max-width: 600px)`.

3. **JavaScript** (lines ~2505–end): Vanilla JS, no framework. Key globals:
   - `wines[]` — in-memory array of all wine objects (source of truth after load)
   - `tastings{}` — map of `wineId → [{date, rating, note, format, qty}]`
   - `valueCache{}` — quarterly snapshot cache to avoid recalculating
   - `sortCol`, `sortDir`, `editId`, `deleteId` — UI state

## Data Layer

**Supabase** is used as the backend (raw REST API, no SDK):
- `SB_URL` and `SB_KEY` are hardcoded constants in the JS section
- Three tables: `wines`, `tastings`, `value_snapshots`
- All DB calls go through `sbFetch(path, options)`, a thin fetch wrapper that adds auth headers
- The app falls back to the hardcoded `SEED` array if Supabase is unreachable

**Data model mapping** (`rowToWine` / `wineToRow`):
- App uses camelCase (`prixBouteille`, `drinkFrom`) — DB uses snake_case (`prix_bouteille`, `drink_from`)
- Wine type: `"primeur"` (futures, bought before delivery) or `"spot"` (already in cellar)
- `livre: true` = physically in cellar; `livre: false` = ordered but not yet delivered
- `shelf` (1–6), `slotCol`, `slotRow` — optional physical position anchor for the Cellier 3D page (see below); the valid `slotCol`/`slotRow` ranges depend on the shelf (11×4 for shelves 1–5, 6×2 for shelf 6). Nullable; most records have none.
- `critic_score`, `critic_source`, `critic_summary`, `critic_url` (added September 2026) — a stored critic review snippet per wine, mapped 1:1 to `criticScore`/`criticSource`/`criticSummary`/`criticUrl` in `rowToWine()`. Read-only from the app's perspective: `wineToRow()` deliberately does NOT include these fields, so the edit-form's PATCH never touches/overwrites them — they're only ever written by a manual research pass (bulk SQL UPDATE), not through the UI. See "Critic review button" below.

## Key Features

**Add/Edit wine**: `openAdd()` / `openEdit(id)` → modal form → `saveWine()`. If `drinkFrom`/`drinkTo` are missing, `saveWineWithLookup()` calls the **`drinking-window` Supabase Edge Function** (deployed at `${SB_URL}/functions/v1/drinking-window`), which proxies to `claude-haiku-4-5` server-side. The Edge Function requires `ANTHROPIC_API_KEY` set as a Supabase secret. Do not call the Anthropic API directly from the browser.

The `f_domaine` and `f_vin` fields have custom autocomplete dropdowns (`setupAutocomplete()`). `f_domaine` suggests unique château names already in `wines[]`; `f_vin` suggests names from `APPELLATION_MAP`. Keyboard navigation (↑↓ Enter Escape) is supported. Both are initialised in the `DOMContentLoaded` listener.

**Tasting log**: `openDrink(id)` → log entry with date, rating (1–5 stars), note, format (bouteille/magnum), qty → saved to Supabase `tastings` table. Drunk bottles are subtracted from displayed stock in the inventory. All tastings are now loaded upfront at startup via `loadTastings()` (called inside `load()`), so `getDrunkCount(wineId)` is always accurate on every page.
- **Editing an existing tasting entry** (added September 2026, `index.html` only): each row in the drink log (`renderDrinkLog()`) now has a ✎ `log-edit` button next to the ✕ `log-del` one. Clicking it calls `editTasting(wineId, idx)`, which reopens the same `#drinkOverlay` form pre-filled from that entry and sets module-level `editingTastingIdx` (the entry's index within `tastings[wineId]`, reset to `null` by `openDrink()`). `saveDrink()` branches on `editingTastingIdx`: when set, it PATCHes via the new `updateTastingInDb(id, entry)` and replaces the entry in place instead of inserting; the save button's label (`#d_save_btn`) swaps between "Enregistrer" and "Mettre à jour" accordingly. The over-stock confirm check excludes the entry being edited from its own stock tally, or editing an entry without changing its qty would spuriously warn. `deleteTasting()` also clears/shifts `editingTastingIdx` if the deleted row was (or came before) the one currently being edited, since array indices shift after a splice.

**"Que boire" wizard**: 3-step questionnaire (occasion, dish, mood) → `generateRecommendations()` scores in-cellar wines using a local algorithm (no API call) that weighs drinking window, appellation, food pairing, and wine age.

**Portfolio value** (`valeur` page): `openValueTracker()` calculates estimated market prices via `estimateMarketPrice(w)`. Prices are looked up via two keys: `dom_firstWordOfVin_vintage` first (disambiguates multi-cuvée domains like Louis Jadot), then `dom_vintage` as fallback; finally appellation/age multipliers applied to purchase price. `dom` = domaine lowercased with the `Château`/`Chateau` prefix stripped — articles like "la", "les", "clos" are **not** stripped (e.g. `'la clef de voûte_2022'`, `'clos floridène_2021'`). Results are saved quarterly to Supabase `value_snapshots` (`VALUE_VERSION = 'v7'`); bump this constant to force recalculation. The table now shows 6 columns: Domaine+Appellation | Stock | Achat | Marché+CHF/btl | +/− | %.

**Critic review button** (added September 2026, both apps): a small round button showing a curated critic snippet (score, critic name, a short original-French paraphrase — never a verbatim quote, for copyright reasons — and an optional "read more" link), stored per-wine in `critic_score`/`critic_source`/`critic_summary`/`critic_url` and populated by a one-off research pass rather than any live API.
- `index.html`: the button (`#modalCriticBtn`, 🍷) sits to the left of the `<h2 id="modalTitle">` title inside `.modal-title-row`, in the edit modal (`openEdit()` shows it only when `w.criticSummary || w.criticScore` is truthy; `openAdd()` always hides it since a new wine has no id yet to look up). Clicking it calls `openCriticPopup(editId)`, which fills and opens `#criticOverlay` (a `.critic-modal` — score, source, summary, and a "Lire la critique complète ↗" link when `criticUrl` is set); `closeCriticPopup()` closes it.
- Cave YD (mobile): the button sits inside `WineSheet`'s crest header, to the left of the domaine name (`hasCritic` check on the same fields), 🗨 rendered via a new `quote` entry in the `Icon` paths dict. The crest header's padding was bumped slightly (`15px 16px 14px` → `17px 16px 16px`) to give the button room. Clicking it opens `CriticSheet`, a second stacked bottom sheet (`.overlay`/`.sheet` at `zIndex:50/51` so it layers above `WineSheet`'s own sheet) showing the same score/source/summary/link, with the link opening `criticUrl` via `window.open(..., '_blank', 'noopener')` (the sandboxed viewer blocks `<a download>` but a plain new-tab `window.open` for an external https URL is fine).
- Both apps' summaries are original French paraphrases the research pass wrote, not reproductions of the critic's own wording — if you regenerate `critic_summary` values, keep doing it that way rather than copy-pasting text off a review page.

**Analyses page**: 6 Chart.js 4.4.1 charts (canvas elements) + an SVG France map showing bottle counts by wine region. Charts are re-instantiated on each `openAnalyses()` call using the `aCharts` object; always call `chart.destroy()` before recreating.

**Primeurs page** (`openPrimeurs()`): Tracks the current-year primeur buying campaign. Shows:
- Two stat tiles: total CHF spent, total bottles + magnums bought.
- A purchase table listing all wines where `type === 'primeur'` and `date` starts with the current year, sorted by château.
- A multi-vintage tile (Bordeaux wines only, via `getRegion()`) showing châteaux held across 2+ distinct vintages. Châteaux bought this year are highlighted in gold; vintages purchased as this year's primeurs are highlighted in oxblood. Bottle counts reflect actual remaining stock using `getDrunkCount()`.
- "This year" is always `new Date().getFullYear()` — no hardcoded year.

**Cellier 3D** (`openCellier3D()`): A Babylon.js (CDN 8.37.1, `babylon.js` core build — PBR materials, no build step, same CDN pattern as Chart.js) visualization of the physical cellar, a Haier HWS247GGU1 (~1900×597×714mm). **Rewritten from Three.js to Babylon.js in September 2026** for PBR reflections/glass, an orbiting `ArcRotateCamera` (mouse + touch), a real hinged/animated glass door, soft shadows, and warm interior LED strips (see "Babylon.js rewrite" below). At the same time the shelf model was rebuilt to match the fridge's actual internal layout instead of a uniform 7×7×5 grid — see "Physical shelf model" below. No wines had a `shelf` assigned when this changed, so no data migration was needed; if that's no longer true next time the model changes, check `select count(*) from wines where shelf is not null` first.

- **Physical shelf model — settled after several wrong axis interpretations, confirmed directly against the real unit**: `SHELF_COUNT = 6` (shelf 1 = top … shelf 6 = bottom). Depth is **not a slot dimension at all** — bottles lie down base-to-wall or base-to-door, one bottle's length fills essentially the whole cabinet depth, there's no front-to-back stacking. What actually varies: **"col"** = position across the *width* (`shelfRowLen(shelfNum)`: 11 for shelves 1–5 via `TIER_ROW_LEN`, 6 for shelf 6 via `BASE_ROW_LEN`) and **"row"** = which vertically-**stacked line** within the shelf's height gap (`shelfRowCount(shelfNum)`: 4 lines via `TIER_ROWS` for shelves 1–5, 2 via `BASE_ROWS` for shelf 6) — "the line on top is the same but exactly the opposite" (the user's own description). Total capacity 5×(11×4) + 6×2 = 220 + 12 = 232. `shelfIsBase(shelfNum)`, `shelfRowLen`, `shelfRowCount`, `shelfCapacity` are the shared helpers — always go through them rather than hardcoding counts, since the two tier shapes differ. **Shelf 1 (top) is known not to match this yet** — the user asked to set it aside for a later pass; shelves 2–6 follow the model above.
  - Within a line, columns interlace 6 bottles one way with 5 the other way (`slotIsWallFacing(shelfNum, row, col)`'s `colIsEven` split — "wall-facing": bottle base at the back wall, neck toward the glass door; "glass-facing": the reverse), and which parity leads flips from line to line (`slotIsWallFacing`'s `rowIsPrimary` check) — this function already had exactly the right shape for this the first time it was written; only the *rendering* axis it was applied to was ever wrong, not the function itself.
  - **This model went through real trial and error, worth knowing before changing it again**: an earlier pass had `TIER_ROW_LEN` as a *depth* count (11 → 6 → 2, chasing a "bottles nest front-to-back" theory) and used `slotIsWallFacing` to nudge alternating bottles *sideways* (a position jitter) to fake interlocking. Reported directly against live screenshots, twice: first the overlap read as one fused "sausage" (too-tight depth-nesting spacing), then — after removing the jitter entirely to fix that — the user pointed out the *entire depth-stacking premise* was wrong: "row of 6... back against the wall, then 5 back against the door... one line, then the line on top is the same but exactly the opposite... each floor has 4 lines". That's what led to the current col=width/row=vertical-stack model. The lesson: a position *jitter* on the interlaced bottles reads as a messy zigzag, but a *rotation-only* flip (no position change) reads correctly as interlocked — see `cellier3DSlotPosition`/`refreshCellier3DBottles` below for how that's applied now.
- **Bottle scale** was guessed independently of the cabinet's real-world size and came out ~2.5–3× too small — caught by the same direct-measurement feedback above ("the bottles are too small"). Fix: `fridgeD` (1.35 scene units) is the real 714mm cabinet depth, so **1 scene unit = 0.529 real meters** (scale factor 1.8908 scene-units-per-real-meter) — any new geometry in this scene (a prop, a bottle variant, anything) should be sized as `real_meters × 1.8908`, not eyeballed against existing (possibly also-wrong) geometry, or the same mismatch recurs silently. Current bottle dims (`initCellier3DScene()`, `sourceBottles` builder): `bodyRadius 0.076, bodyLen 0.38, neckLen 0.14, neckRadius 0.02, capLen 0.05` (~80mm × 300mm real bottle, body:neck:cap split ~67:25:8%).
  - At this corrected size, 11 bottle-widths don't fit the shelf width without touching — real interlocking bottles achieve that by sitting at slightly different depths, not by being narrower. `cellier3DSlotPosition` gives alternating columns (by `slotIsWallFacing`) a small depth offset (`bodyRadius * 1.05` either way) for exactly this reason — X stays perfectly evenly spaced (so the row still reads as straight from the front), only Z varies. Don't remove this offset without re-checking bottle-diameter-vs-column-spacing; it's not cosmetic, it's what keeps adjacent bottles from geometrically overlapping.
- **Position model**: a wine entry stores ONE manually-chosen anchor slot (`shelf`/`slotCol`/`slotRow`), not one coordinate per physical bottle. Its currently-remaining bottles/magnums (via `getDrunkCount`) render sequentially from that anchor, row-major (col 1→N, then next row, N depending on the shelf's tier type). If a wine's count overflows its tier past its anchor, the overflow "stacks" visually above the shelf rather than spilling onto another shelf.
- **`computeShelfOccupancy(shelfNum, excludeWineId)`** is the single shared layout algorithm — used by both the edit-modal slot picker AND the 3D renderer, so they can never drift out of sync. Each returned cell now also carries `wallFacing` (from `slotIsWallFacing`) so both consumers render/pick the correct bottle orientation. Fully-drunk wines are skipped automatically (no manual slot cleanup needed when a bottle is finished).
- **Shelf numbering**: shelf 1 = top ("haut"), shelf 6 = bottom ("bas"). `cellier3DShelfY(shelfNum, shelfGap)` is the single source of truth for this mapping — used by both the shelf meshes and the bottle placement. Don't compute shelf Y positions ad hoc elsewhere.
- **Slot picker**: the edit modal (`openEdit`/`saveWine`) has a "Position dans la cave" field group with a shelf `<select>` (1–6) and a clickable grid (`renderSlotPicker()`) whose column count is set inline per shelf (`grid.style.gridTemplateColumns`, 11 cols for a nested tier, 6 for the base tier — CSS no longer hardcodes 7) showing free/occupied/selected cells live, scoped to the wine being edited via `excludeWineId`. Glass-facing cells get a `.slot-glass-facing` tint so the nesting pattern is visible while picking.
- **Babylon.js rewrite** (`initCellier3DScene()`, lazy-initialized on first visit, not torn down/recreated on revisit — only `refreshCellier3DBottles()` re-runs on data changes): `ArcRotateCamera` gives free orbit/pan/zoom out of the box (mouse drag + wheel, and touch — `touch-action:none` is set on the canvas). The cabinet is matte-black PBR (`PBRMaterial`, low metallic/high roughness — a highly reflective/metallic finish makes it read as grey under IBL, not black), built from open panels (back/sides/top/bottom), NOT a closed box — a solid box's opaque front face would hide everything inside. A single glass door (`PBRMaterial`, low alpha, low roughness) is parented to a `TransformNode` hinge pivot **on the right edge** (moved from the left after the user corrected the handle side against the real unit's actual opening direction — the door plane itself is symmetric and needed no change, but `doorFrameRoot.scaling.x = -1` mirrors the Blender-built frame asset so its baked-in handle lands on the new non-hinge edge instead of regenerating the GLB; `cellier3dToggleDoor()`'s open-rotation sign flipped too, from `-Math.PI*0.42` to `+Math.PI*0.42`, or it would swing into the cabinet instead of out) and animates open/closed via `cellier3dToggleDoor()` (`BABYLON.Animation.CreateAndStartAnimation` on `rotation.y`) triggered from a toolbar button; `cellier3dResetView()` restores the camera's initial alpha/beta/radius/target. Two thin emissive `unlit` PBR strips on the interior side walls plus a `GlowLayer` and a warm `PointLight` give the "appliance interior light" look — keep `emissiveIntensity`/`glow.intensity` low (≈0.35–0.6) or the strips blow out to solid white in the bloom. `scene.environmentTexture` is Babylon's hosted `environmentSpecular.env` (IBL reflections only, no visible skybox mesh) — keep `scene.environmentIntensity` low (≈0.2–0.3) for a black cabinet to actually read as black rather than reflecting the environment as grey. Bottles are built once as 5 palette-colored "source" meshes (body+neck+foil-cap merged via `BABYLON.Mesh.MergeMeshes` with `multiMultiMaterial` so the cap keeps its own brass material), baked lying on their side (`bakeCurrentTransformIntoVertices()` after `rotation.x = Math.PI/2`, neck ending up toward +Z/the glass door by default), then instanced per slot (`createInstance`) for performance — up to ~232 instances is trivial. A glass-facing slot gets `instance.rotation.y = Math.PI` to flip its neck toward the back wall instead. Bottle colors deliberately avoid the shelf's gold-wood tone (`#7d6024`) so they don't visually blend in.
- **Interaction**: `scene.onPointerObservable` (POINTERMOVE + POINTERTAP, so it works for mouse hover and touch tap alike) picks against `metadata.wineId` set on each bottle instance, showing a floating HTML popover (`cellier3DShowPopover`) with a "Modifier" button that calls the real `openEdit(id)`.

  - **Camera can't orbit through the room wall**: a later pass (the user could freely orbit the camera behind/through the walls) — worth documenting in detail because two different fixes were tried and *looked* plausible before actually verifying with a real drag simulation:
    1. **Mesh-based `checkCollisions` doesn't reliably work for `ArcRotateCamera` orbit-drag** — tried first (`scene.collisionsEnabled = true`, `camera.checkCollisions = true`, `camera.collisionRadius`, `wall.checkCollisions = true` etc.). Direct testing (simulated mouse-drag orbit + read back `camera.position` each step) showed it caught the camera at the back wall in one test but let it sail straight through the (at-the-time-still-present) side wall in another — even at a slow, frame-by-frame drag speed, not just a fast-drag tunneling edge case. `ArcRotateCamera` recomputes `position` from `alpha`/`beta`/`radius` via trigonometry every frame, and pointer-drag orbit input mutates `alpha`/`beta` directly — the mesh collision system doesn't intercept that path the way it does a `FreeCamera`'s translational movement. `checkCollisions`/`collisionRadius` were left set on the camera and `floor.checkCollisions` as a harmless secondary layer, but don't rely on mesh collision alone for this.
    2. **Directly setting `camera.radius` each frame in `scene.onBeforeCameraRenderObservable` also didn't stick** — computed the correct safe radius every frame (verified by logging), but something in Babylon's own per-frame camera update overrode it back to the old, unsafe value most frames anyway. Never fully root-caused *why* (plausibly some internal inertia/offset reconciliation specific to how radius is derived) — not worth chasing further once the actual fix was found.
    3. **What actually works**: retune `camera.upperRadiusLimit` itself every frame, in `scene.onBeforeCameraRenderObservable`, to whatever distance the current view direction can safely travel before crossing the wall — Babylon's *own* internal radius clamp then enforces that limit using its own already-correct mechanism, instead of a custom clamp racing it. Direction vector from `alpha`/`beta`: `dirZ = sin(alpha)*sin(beta)` (Babylon's own spherical-position convention — position = target + radius·(cos(alpha)*sin(beta), cos(beta), dirZ)); if it points toward the back wall (`dirZ < 0`), compute the distance along that ray to the wall plane (minus a small margin) as the new `upperRadiusLimit` (floored at a small constant like 0.3, never `camera.lowerRadiusLimit` — see the next point for why). Verified by simulating a full-circle drag with varying vertical movement and sampling `camera.position` after every step: 0 violations across 260 samples, vs. sailing meters past the wall before this fix. (This originally also constrained a left side wall via a second `dirX` term — the side wall was removed shortly after per the user's own follow-up feedback, "it is annoying for navigation"; if a side wall is ever reintroduced, restore that term rather than re-deriving it.)
    4. **`camera.lowerRadiusLimit` had to come down further too (1.9 → 0.45)** — independent of the dynamic-`upperRadiusLimit` fix above, but it was actively fighting it: at many orbit angles the wall is *closer* than 1.9 (the room is small — the wall sits ~0.69 from target), so whenever the dynamic clamp tried to pull the camera in close enough to stay in front of it, Babylon's own `lowerRadiusLimit` enforcement immediately pushed it back out past that same wall, every frame, netting no improvement. `cellier3dLocateWine()`'s close-up zoom-in distance was also detached from `camera.lowerRadiusLimit` (it used to animate `radius` to that value directly) to a fixed `0.9`, since tying a "nice view of one bottle" distance to a limit that's now deliberately very small for a different reason would have zoomed in far too close.

    - **Axis conversion is the recurring gotcha** — Blender's own axes are X=width, Y=depth, Z=up; this app's scene (and glTF/Babylon after export) uses X=width, Y=height(up), Z=depth. They are *not* the same order. `build_cabinet.py` has `B(x,y,z)` / `BD(w,h,d)` helper functions that convert an authored-in-Babylon-space position/dimension into the Blender-space tuple bpy expects — use them (or equivalent) for any future Blender asset in this app, authoring everything in Babylon-space coordinates and converting once at the call site, rather than trying to hand-convert each position. `build_tray.py` did NOT have this helper and got it wrong once (put a slat's long across-depth dimension into Blender's Z/up slot by accident, which only exported as broken — a meter-tall standing fin instead of a flat plank — while looking completely fine when re-imported into Blender to preview, because that re-import undoes the exact same conversion mistake). **The only reliable way to verify a Blender→glTF axis conversion is correct is to inspect the exported file's raw JSON node `scale`/`translation` values directly** (GLB = 12-byte header + 4-byte JSON-chunk-length + JSON chunk — `struct.unpack('<I', data[12:16])[0]` gives the JSON length, `json.loads(data[20:20+that_length])` parses it) or load it into the actual target engine (Babylon) and screenshot it — never trust a Blender-side re-import/render as proof the export is correct.
    - Every asset's parts are parented to **one root empty** before export (`parent_all_to_root()` in `build_cabinet.py`, inline in `build_tray.py`) — **required**: without a common parent, Blender's glTF exporter emits one root node per object, and Babylon's `AssetContainer.instantiateModelsToScene()` only returns `entries.rootNodes[0]`, silently dropping every other part.
    - Materials: **glTF export only supports simple Image Texture nodes or flat factors, not procedural shader node graphs** — `ShaderNodeTexWave`/`ShaderNodeValToRGB`/etc. get silently dropped, exporting as a flat default-white material. This bit once already this session (see "Blender for texture baking" below). The tray slats' material loads an already-baked JPEG (`beech_wood.jpg`, written into the scratchpad by the earlier texture-baking pass) as a plain `ShaderNodeTexImage`; the cabinet/frame/rails all just use flat `Base Color` factors (also exports fine).
    - Loading a GLB into Babylon: **`data:;base64,<data>` URLs are unreliable for `BABYLON.SceneLoader`** — its path-resolution logic can trip over `/` characters that legitimately occur in the base64 payload. Convert to a `Blob` + `URL.createObjectURL()` instead (see the shared `loadGlbContainer()` helper inside `initCellier3DScene()`) and load that URL with `LoadAssetContainerAsync`; revoke the blob URL right after the load resolves. `initCellier3DScene()` and `openCellier3D()` are both `async` for this — `await` every container load *before* the `c3d = {...}` assignment further down, or `refreshCellier3DBottles()` (called immediately after `initCellier3DScene()` in `openCellier3D()`) will silently no-op against a `c3d` that isn't set yet.
    - `receiveShadows` must be set on a container's own (source) meshes — `container.meshes.forEach(m => m.receiveShadows = true)` — *before* calling `instantiateModelsToScene()`; setting it on an already-created instance is a silent no-op (Babylon logs a console warning if you get this backwards).

The tray loads once and is instantiated per shelf via `trayContainer.instantiateModelsToScene()` (creates lightweight `InstancedMesh`es, not full clones — cheap for 6 shelves).
  - **Blender for texture baking** (a separate, narrower use of Blender than the geometry above): `BEECH_TEX_B64`'s source JPEG was baked via Blender's Python API in headless mode — a procedural wave-texture + noise-texture node material (thin light streaks over a dark base via a tightly-clustered `ColorRamp`, NOT a broad 50/50 zigzag — that reads as cartoonish) baked to a diffuse image and exported as JPEG for a compact base64 size. ## Appellation & Domaine Conventions

All `vin` and `domaine` values in the database follow strict canonical spelling. **Always use these exact forms** when adding or editing records:

- Domaines: full `Château` with accent, capitalised article (`Château Les Gravières`, not `Château les Gravières`)
- Appellations use the `APPELLATION_MAP` array in the JS as the single source of truth. Do not add free-form text, years, classification ranks (Grand Cru Classé, 5ème, etc.), vineyard names, or AOC suffixes to the `vin` field. Examples of correct forms: `Saint-Émilion Grand Cru`, `Pessac-Léognan`, `Moulis-en-Médoc`, `Lalande-de-Pomerol`, `Savigny-lès-Beaune`.
- When adding new appellations, add them to `APPELLATION_MAP` first (with `name` and `region`), then use the `name` value in the database.
